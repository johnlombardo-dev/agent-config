# Global Agent Operating Guide

## Global Copy Quality Rules

These rules apply to all copy generated by any agent or skill: headings, eyebrows, section intros, button labels, and descriptive text. The goal is to produce writing that is useful, precise, and worth reading - never decorative or vague.

---

### 1. Purpose of copy

Every piece of copy must earn its place.

A sentence, heading, or label is only acceptable if it does at least one of:

- Orient the reader (what this is, who it is for, where they are in the product).
- Differentiate (what is unique or constrained about this thing).
- Set expectations (what the user will see, do, or get next).
- Reduce uncertainty (edges, limits, prerequisites, caveats).
- Enable action (what the user should try, configure, or avoid).

If a sentence does **none** of these jobs, it must be removed or rewritten.

---

### 2. Copy value tests

For every headline, eyebrow, section intro, and paragraph:

Ask these three questions:

1. If I delete this, does the section become less clear or less actionable for a first-time visitor?
2. Does this say something the title or heading does **not** already say?
3. Would a user ever quote this line when explaining the product or feature to someone else?

If the answer is **"no"** to all three, the sentence is decorative.  
Decorative sentences are not allowed. Delete or replace them with something that passes at least one test.

---

### 3. Hero and first-contact pages

For any page that is likely to be a first contact (homepages, landing pages, top-level docs):

1. **Lead with the product, not the architecture.**
   - First sentence: state what the product is and who it is for, in plain language.
   - Second sentence: state what problem it solves or what it lets the user build.
   - Only after this, introduce patterns, contracts, and internal terminology.

2. **Headlines must define category and benefit.**
   - Hero headlines must name the product category (e.g. "React dashboard components", "Configurable monitoring panels") and the primary benefit.
   - Do not use headlines that are only evocative or clever ("surface", "ceremony", "experience") without clear meaning.
   - If a headline cannot be understood by a new visitor in isolation, rewrite it.

3. **Eyebrows and subheads must add context.**
   - Eyebrow text is for scope, domain, or audience (e.g. "React components", "Server dashboards", "Host integration"), not slogans or taxonomies.
   - Do not use unexplained internal labels like `PANEL + STORE + DASHLET` as the only context.

4. **Primary actions must have a clear path.**
   - Present a small number of primary actions in a sensible order:
     - Explore or try the thing.
     - Learn how it works or see an example.
     - Install or integrate.
     - Read detailed documentation.
   - Avoid presenting four or more competing actions before the product has been explained.

---

### 4. Jargon, metaphors, and "vibe" language

#### Jargon

- Technical terms are allowed, but only **after** the product's purpose is clear.
- When introducing a term (e.g. "Dashlet", "host store", "scenario state"), pair it with concrete behavior:
  - What it does.
  - Where it appears in the UI.
  - How it affects the user's workflow.
- Do not assume the reader knows internal vocabulary on first encounter.

#### Metaphors and vibe phrases

- Do not use metaphors or vibe phrases in core explanatory copy unless they improve understanding.
  - Examples of disallowed vibe terms when they replace explanation: "surface", "ceremony", "specimen", "journey", "experience", "intentional summaries".
- If a metaphor makes the text less precise or harder to parse, remove it.
- Clever or "memorable" lines are not acceptable if they reduce clarity or specificity.

---

### 5. Technical details and implementation language

- Technical details must always be connected to a user-visible outcome or constraint.
  - Good: "This panel uses your existing store, so you can add dashboards without rewriting state."
  - Weak: "This panel uses actual values from the host store while staying independent from local scenario state." (missing "so that...").
- Do not lead with implementation language (patterns, contracts, schema names) in hero copy.
- Debug-style metadata (e.g. "placement mode: floating", "store contract: native Store") belongs in:
  - reference docs,
  - "How it works" sections,
  - or advanced/implementation notes - not in first-contact explanations.

If you cannot explain **why** a technical detail matters to the user, omit it from first-contact copy.

---

### 6. Banned patterns and words

Avoid the following unless they are backed by concrete, verifiable detail in the same paragraph:

- Generic value claims: "useful", "powerful", "seamless", "modern", "next-generation", "without the ceremony".
- Abstract nouns without grounding: "surface", "experience", "journey", "workflow" (on its own).
- Internal metaphors and labels: "specimen", "scene", "operating surface", "intentional summaries", "host-first" (without explanation).

Replace them with:

- Specific nouns: "panel", "widget", "React component", "dashboard", "metric".
- Specific verbs and outcomes: "move panels", "add live metrics", "reuse dashboards across hosts", "bind to your existing store".

---

### 7. Style for component and API documentation

For documentation pages (components, APIs, patterns):

- Describe each entity's purpose in **one factual sentence** before any jargon:
  - "This panel component renders a configurable dashboard area bound to your app's store."
- Document behavior in terms of **what the user can do**, not just how it is implemented.
- Examples should be realistic and tied to concrete scenarios, not placeholder language or abstract "demo" concepts.
- Avoid marketing language entirely. Documentation is a technical tool, not a sales surface.

---

Agents and skills must follow these rules when generating, critiquing, or editing copy.  
When in doubt, choose plain, concrete language that helps a new visitor understand what the product is, what it does, and what they can do next.
